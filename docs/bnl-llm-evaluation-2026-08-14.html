Which models earn their keep on a natural-language-to-DSL task

We put all four models on inference0-api.sdcc.bnl.gov through the same 25-case suite: translating a user's plain English into a small, strict query language over a scientific file catalog. Two models scored perfectly, one is unusable for this workload, and one proxy setting is failing requests outright.

The task, for readers outside the project

Think text-to-SQL, but against a smaller and stricter language. Our application is a web UI over a file catalog holding roughly 100 million data files produced by a large physics experiment. The catalog speaks its own query language — MQL, the MetaCat Query Language — which is SQL-shaped but purpose-built: a few dozen grammar rules, no joins in the SQL sense, and its own operators for set algebra and lineage.

A user types "raw files from run 27731" and the model must emit a valid MQL query. What makes this a sharper benchmark than general text-to-SQL is that the vocabulary is closed and the failure mode is silent. Every identifier the model may use — 13 partition names, 7 attribute names, 2 server-side functions — is supplied in the prompt, and anything outside that list is a hallucination. Crucially, a hallucinated identifier usually still parses: the query runs, returns zero rows, and reads to the user as a legitimate "no results found".

Four schema terms appear in the test cases. In ordinary database terms:

namespaceA top-level partition of the catalog, like a schema. There are 13, each named for the instrument that produced the data. Addressed as namespace:dataset.
datasetA named collection of files inside a namespace — the closest thing to a table.
core.runsAn integer ID for one data-acquisition session. The single most common filter users write.
core.data_tierAn enum-like string for processing stage: 'raw' straight off the instrument, 'full-reconstructed' after the processing pipeline. Users say "raw" and "reco", so the model must map informal vocabulary onto exact values.
parents / childrenLineage edges. Every derived file records which files it was produced from, so the catalog is also a DAG the language can walk.

Instrument names in the test asks — "ProtoDUNE horizontal drift", "Iceberg", "NP04 beam" — are an entity-linking step: each must be resolved to its namespace identifier using a lookup table supplied in the prompt. That is deliberately the same shape of problem as resolving a user's informal table name against a real schema.

One caveat on all of this: ours is a single workload — structured translation into a constrained DSL with a hard no-hallucination requirement. It rewards grounding and punishes creativity, so it should inform your roster decision, not settle it. A model that looks poor here may be the right one for summarisation or code assistance.

What we measured, and why

A model is only useful to us if the query it writes is one we can actually run, so the gates run cheapest-signal-first. None of them collapses into the others: a model can score 100% on syntax and still be useless because the query means the wrong thing.

jsonDid it honour the response contract at all — one JSON object, no prose around it.
parsesThe query parses against the DSL's real grammar. We load the actual Lark grammar out of the catalog client library, so our checker cannot drift from the server's parser.
semanticsDoes it mean what was asked. Per-case assertions on the constructs and literal values that must appear.
groundedNo invented identifiers — partition, attribute, or server function. This is the metric that separated the field.
adherenceObeys prompt rules that a perfectly valid query can still break. One legal query shape expands to 22,000 partitions server-side and times out; the prompt forbids it.
repairWhen it does emit a syntax error, can it fix it when handed the parser's message? Production allows exactly one retry.
refusal calibrationRefuses the genuinely impossible without refusing the merely unfamiliar. Both directions are failures.
latencyp50 / p95 / max wall clock. This sits in an interactive web UI, so p95 matters more than p50.
determinismSame prompt, temperature 0, three times: identical output?
api_compatDoes the endpoint accept the request parameters we send. A rejected parameter fails the whole request, so this is pass/fail, not a nicety.

The suite

Nine tiers of ascending difficulty. The numbering is real: tiers 1–4 are ordinary lookups, 5–6 exercise the harder corners of the language, and 7–9 are traps where the tempting answer is the wrong one.

2 · filters (4) Predicates on IDs, enums, counts, ranges; informal→exact vocabulary raw files from run 27731 in ProtoDUNE horizontal drift files where namespace = 'hd-protodune' and core.runs in (27731) and core.data_tier = 'raw'
3 · dates (2) Date construction, key-absence, deterministic ordering the first 10 raw files in iceberg taken after April 2024 files where namespace = 'iceberg' and core.data_tier = 'raw' and core.start_time > datetime('2024-05-01') limit 10

…not the wildcard form, which expands to 22k partitions and times out

…still one JSON object, no chain-of-thought preamble

Tier 7 is where the field separated. Each trap has the same structure: the plausible answer is a well-formed query containing one identifier that does not exist. Nothing downstream catches that — a grammar check passes it, and the user sees an empty result set rather than an error.

Per-model findings

gemma-4-26b

overall100% p500.31s p950.46s out tok48
  • Clean sweep, and the fastest by a wide margin — p95 under half a second on a 3.4k-token prompt.
  • Handled every advanced construct: set difference, union, intersection, both lineage directions, and sampling.
  • Told that one sampling function isn't installed, it substituted the available equivalent — filter hash(3, 0) — rather than refusing.
  • Terse explanations (48 output tokens median). Fine for us; a UI that leans on the explanation might prefer gpt-oss.
  • Rejects reasoning_effort with HTTP 400 — see the service-level note below.

gpt-oss-120b

overall100% p500.89s p951.47s out tok253
  • Also a clean sweep, with the best explanations in the field by a distance. On the missing-attribute trap it wrote: "The request asked for beam energy = 7 GeV, but no metadata key for beam energy exists…" — exactly what a user needs to see when a filter is silently dropped.
  • Refused both impossible asks with a correct reason, including noting the language is read-only when asked to delete.
  • The only model that accepts reasoning_effort, making it the one model our production request body works with unmodified.
  • ~5× gemma's output tokens. That's the cost of the better explanations, and a fair trade when the text is user-facing.

nemotron-3-ultra-550b-nvfp4

overall100% p502.19s p955.26s max10.17s
  • Scored as well as the leaders — no accuracy complaint at all.
  • But 7× gemma's p50 and 11× its p95, with a 10s worst case. In an interactive query builder that's the difference between instant and visibly waiting.
  • Not stable across runs. The three-repeat check passed, but between our two full runs — same prompt, temperature 0 — it answered the sampling-function case differently: a refusal the first time, the correct filter hash(3, 0) the second. Worth investigating on your side whether batching or non-deterministic kernels explain it.
  • Our read: for this task, 550B buys nothing over 26B. It may well earn its place on harder workloads; it doesn't on this one.

llama-4-scout-17b

overall84% grounded22/25 p500.53s

Fast and format-obedient, but it failed every grounding trap — and each failure produces a query that looks correct:

  • core.beam_energy = 7 — invented an attribute that does not exist in the schema. The query runs and silently matches nothing.
  • namespace = 'sbnd' — invented a partition for an instrument that isn't in this catalog, instead of saying so.
  • filter every_nth(3) — called a server function that isn't installed, so the query errors at execution. It also passed one argument where the function takes two.
  • One genuine syntax error — files from iceberg where …, using a partition name where the grammar requires a fully-qualified partition:collection. To its credit it repaired that correctly on the first retry when handed the parser message: 1/1 repairs succeeded.

Silent wrong answers are the one failure mode we cannot mitigate downstream. Our validator catches bad syntax, but a well-formed query against an invented identifier parses cleanly and returns an empty result that reads as a real finding.

Service-level findings

Actionable

Three of four models reject reasoning_effort with HTTP 400, failing the entire request:

litellm.UnsupportedParamsError: openai does not support parameters:
['reasoning_effort'], for model=gemma-4-26b-a4b-it.
To drop these, set `litellm.drop_params=True` or for proxy: ...

The error text names the fix. Setting drop_params=True on the proxy would let clients send one request body across your whole roster instead of maintaining a per-model parameter matrix. We had to add a config knob to work around it, and every other client will hit the same wall. Only gpt-oss-120b accepts the parameter today.

  • Latency looks too good to be uncached. 0.31s p50 from a 26B model on a 3.4k-token prompt suggests prompt caching is doing real work — our system prompt is static across requests, so that's plausible. If so it's a genuine strength worth documenting; we'd like to know whether a cold first request is materially slower, since that's what a user's first query of the day would hit.
  • response_format: {"type":"json_object"} works on all four models. That matters a lot for us and is worth keeping as a compatibility guarantee.
  • /v1/models and token accounting both behave. Usage figures came back populated on every request, which is what let us report output-token cost per model.
  • Served model IDs differ from the advertised ones. The 400 above reveals gemma-4-26b is actually served as gemma-4-26b-a4b-it. Not a problem, but a version manifest would help us report issues precisely and notice when a model changes underneath us.

Method and limits

Scoring uses the production system prompt, so these numbers describe the shipped feature rather than a synthetic proxy. Validation is offline: we parse each query with the DSL's real grammar and check every identifier against the closed lists. We deliberately do not execute all 100 generated queries against the production catalog — a broad query can run for minutes, which would dominate the runtime and load a shared service. The function whitelist was derived from the live server once, which is how "that sampling function isn't installed" is caught without a network call.

Three honest limits:

  • Semantic checks are exact-substring assertions, so a correct paraphrase we didn't anticipate would be marked wrong. We hand-reviewed every failure in this report; none was a false positive.
  • Single-request latency with no concurrency. Nothing here says how these models behave under simultaneous load, which is probably the number you care about most.
  • 25 cases is enough to separate the field, not enough for a tight confidence interval on a 4-percentage-point difference.

The harness is open source and re-runnable. It reads /v1/models, so it picks up roster changes automatically:

git clone https://github.com/czczc/dunecat
uv run scripts/llm-bench.py            # all models the endpoint lists
uv run scripts/llm-bench.py gemma-4-26b gpt-oss-120b

Happy to re-run it against a candidate model or a changed proxy config, and to share the raw per-case JSON output.
